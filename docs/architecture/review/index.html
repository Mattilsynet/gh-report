DDD Pattern Review — cherry-pit substrate

A pattern-by-pattern audit of how well the cherry-pit crate family (cherry-pit-core, -app, -gateway, -merger, -projection, -storage, -wq) realises the tactical and strategic patterns of Domain-Driven Design. Every verdict is decided by source evidence (type/trait names + file:line), cross-read against the binding ADRs (CHE-0004 EDA+DDD+hexagonal, CHE-0005 single-aggregate). Compiled 2026-07-23.
Depth pass (2026-07-23): the "well represented" verdicts below are decided on the trait/type surface. A second, adversarial implementation-body review (Rust-specialist, full file:line evidence in bd bead adr-fmt-t8k35) then asked whether the deep semantics of each surface-solid pattern actually hold in code — no happy-path-only shells, no dropped invariants, no bypass paths. Findings are in the new Depth review section; two Partial downgrades and several tracked gaps result. Surface verdicts are retained (the abstraction is genuinely first-class) but annotated where the realisation is thinner than the name implies.
Language pass (2026-07-23): for the three depth-Solid patterns, a ubiquitous-language consistency check compares the code doc-comments against the governing ADRs term-by-term. Result: strongly consistent coined vocabulary, four minor drifts (L1–L4), no contradictions. L1–L4 were then individually re-verified against source; the L4 finding was corrected (it is a phantom-adapter-roster drift, not the "pardosa removed" claim of the first draft — pardosa is alive and is gh-report's production backend). Remediation (2026-07-23): L1, L2, L3, and L4 have since all been fixed in source (CHE-0042:R3 accessor list completed, CHE-0042 envelope.rs→event.rs path corrected, CHE-0041:R5 citation added to idempotency.rs); the L4 root cause was traced to a delete-then-reintroduce name collision; its store.rs:18 phantom-roster comment has been fixed (commit 9ef607f, CHE-0004). The lower-blast-radius Cargo.toml/test-doc copies of the same stale wording, left unfixed as of that pass, have since also been fixed (commit bd594d7; see L4 root cause residual table).
Framing: cherry-pit is a subtractive substrate — illegal compositions must fail to type-check (AGENTS.md, the Solon stance). Several DDD patterns are therefore deliberately absent, not missing; the report distinguishes "lacking by omission" from "lacking by ratified deferral" wherever an ADR records the choice.

Verdict legend

Well represented first-class trait/type in the substrate, DDD name used verbatim. Partial the responsibility exists but is folded into another construct, or realised without a dedicated named abstraction. Lacking no source trace; either a genuine gap or a ratified deferral (noted per row). By design absent absence is an ADR-ratified design choice, not a gap. Unknown / not checked this dimension was not examined for this pattern in the passes run so far.

Depth review — do the deep semantics hold?

Every pattern in the tactical/strategic tables that scored Well represented was re-examined at the implementation body, adversarially: looking for the panic, the non-determinism, the dropped field, the missing check, the bypass path. The question is not "does the abstraction exist" (it does) but "is the DDD invariant the abstraction promises actually enforced, or only the happy-path shell." Depth verdicts: Solid deep semantics hold; Mixed trait-level solid but a real realisation gap exists; Shallow happy-path only. Full file:line evidence in bd bead adr-fmt-t8k35. The three strategic/tactical rows below Single-writer (Bounded Context, Ubiquitous Language, Invariant enforcement) were added in a D2 coverage extension — full evidence in bd bead adr-fmt-vie4a.

Ubiquitous-language consistency

A pattern is only truly "well represented" in DDD terms if the ubiquitous language is stable across its expressions — the code doc-comments and the governing ADRs must say the same thing in the same words. For the three patterns that scored Solid on depth (Domain Event/Envelope, Value Objects, Repository) this section compares the two prose surfaces directly. Overall the language is strongly consistent — the same coined terms recur verbatim on both sides — with a small set of staleness drifts (never contradictions, always the ADR lagging a shipped change).
Coverage extension (2026-07-23, D2 — bd bead adr-fmt-vie4a): the pass was extended to the five remaining depth-scored patterns — Aggregate, Command, Policy, Projection, Single-writer (Governed/Mixed depth, not just Solid) — since a language check does not require depth-Solid to be meaningful. Four of the five are Consistent, no drift. The fifth (Single-writer) surfaced one genuine drift, since fixed; see below.

Root cause of the L4 confusion — a delete-then-reintroduce name collision

The first draft's wrong "pardosa was removed from the workspace" claim was not careless reading — it was induced by stale and ambiguous documentation. Git history shows two different crate families shared the name "pardosa" across a deletion boundary:

  • Legacy pardosa (pardosa-encoding — a binary Encode/Decode "GenomeSafe" serialization substrate) existed 2026-05-15 → 05-21, then was physically deleted (commit 36f0d74, "S5: physically delete pardosa-* crates from workspace"). DomainEvent was swapped off its Encode bound onto serde the same day (193093e).
  • Current pardosa (the .pgno / NATS "EDA storage layer implementing fiber semantics", the PGN-ADR substrate, gh-report's CHE-0074 backend) was imported ~2.5 weeks later (commit 050e08d, 2026-06-08, "Import Pardosa workspace crates"), reusing the name for an unrelated codebase.

So the doc comments were true when written and became misleading only when a new pardosa was grafted onto the same name. Three stale/ambiguous artefacts propagated the confusion into the review:

Misleading artefactWhy it misledStatus
event.rs:320-323 — "…removed alongside the pardosa crates" The smoking gun: literally asserts "the pardosa crates" were deleted. True for legacy pardosa, plainly false against a tree with 10 live pardosa-* crates. Fixed — reworded to scope the removal to the legacy pardosa-encoding crate and explicitly note the current substrate is live and unrelated.
event.rs:16, Cargo.toml:32, tests/adt_obligations.rs:17 — "Pardosa-encoding has been removed from the workspace" Ambiguous capitalisation/parse: "Pardosa-encoding" (one legacy crate) skims as "Pardosa, encoding" → "pardosa is gone". The Cargo.toml/test copies compound it by repetition. Fixed — event.rs:16 reworded ("the legacy pardosa-encoding crate… unrelated to the current pardosa substrate"). The Cargo.toml:32 and tests/adt_obligations.rs:17 copies, previously left unfixed (marked "Partly fixed" in the prior pass), are now also fixed — stale "ADR cleanup deferred" governance-debt phrasing corrected to reflect the removal is complete (commit bd594d7).
C4 docs — c4/level2-containers.html:81,182, level1-context.html:75 — "pardosa dep explicitly REMOVED" Accurate but easy to over-generalise: these correctly say cherry-pit-core has no pardosa dep (CHE-0010 holds), yet the bare word "REMOVED" reinforces the "pardosa is gone" reading when skimmed out of scope. Left as-is — technically correct for the crate they describe; not a defect, but noted as a contributing amplifier. Could be tightened to "no pardosa dependency (severance, not deletion)".

Lesson. The reusable trap is name reuse across a delete-and-reintroduce boundary: comments written against the first tenant of a name silently become lies about the second. The durable fix is not just rewording — it is never letting a removal comment name a bare identifier (pardosa) that a future crate might re-occupy; scope it to the exact artefact removed (pardosa-encoding) and its reason. The store.rs:18 phantom-roster drift (L4 proper) is the same disease one step removed: the doc names implementations by substrate rather than by the one concrete adapter that actually exists.

Headline findings

  • Surface abstractions are first-class; the depth pass is where the nuance lives. All eight "well represented" patterns carry the DDD term verbatim and are type-enforced at the trait boundary. Under adversarial implementation-body review, five now hold end-to-end (Solid: Domain Event/Envelope, Value Objects, Repository, Policy, Projection/CQRS), two are ratified Governed specializations (Aggregate, Command — CHE-0085:R8, doc-plane, code unchanged), and one remains Mixed (Single-writer — convention doc + tests landed, structural seal deferred; see Depth review, gaps G1–G5).
  • "Partial" here mostly means "folded, not missing" — now ratified. Entity, Factory, and Domain Service have their responsibilities present (identity via AggregateId, validated construction via EventStore::create, pure logic in handle/react) but no dedicated trait — CHE-0020:R5 (8636c0b) now ratifies this as a deliberate design choice rather than an undocumented gap. The ACL is present in hexagonal port form rather than as a named context-map layer.
  • The genuinely absent orchestration patterns are ratified, not overlooked. Saga and Process Manager are deliberately deferred by CHE-0040: compensation is domain-event-driven, timeouts are explicit domain events, failed policy outputs are dead-lettered. The correlation/causation envelope fields are the substrate a saga would use — the orchestrator is a conscious non-goal pre-1.0, re-affirmed after cherry-pit-app shipped. Durable multi-step state, when needed, is modelled as an aggregate (the scheduler, CHE-0081), not a framework process manager.
  • Specification is no longer an unratified gap. It remains absent from source, but CHE-0020:R5 (8636c0b) now ratifies the absence explicitly. Impact is low today (predicate logic lives inline in handle and query resolvers); if reusable business predicates emerge — especially on the read side — a new ADR + a small Specification trait remains the natural future candidate, but it is no longer the corpus's one unrecorded gap.
  • Net assessment. Measured against DDD's catalogue, cherry-pit is a high-fidelity tactical + event-sourcing DDD substrate with strong strategic single-context discipline. Its omissions cluster exactly where the Solon subtractive stance predicts — orchestration machinery and multi-context tooling that would add degrees of freedom the niche (single-writer, intra-org, sub-PB) does not need. No pattern now lacks both code and a ratifying decision (CHE-0020:R5 closed that gap for Specification). The depth pass adds a second axis: even among the type-enforced patterns, the strongest guarantees are on the data plane (immutable envelopes, sealed value objects, TOCTOU-closed store, now also a monotonic checkpoint and a create-time existence guard), while the one remaining un-sealed structural gap is single-writer's composition-root convention (documented and tested, but not type/ownership-sealed) — the surface a saga/process-manager layer, or a future ownership-token seal, would harden further if built.
